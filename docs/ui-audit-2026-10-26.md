## 一、结论摘要

| 等级 | 数量 | 含义 |
| --- | --- | --- |
| **P0** | **7** | 用户直接可见 / 数据串号 / 无缓存放大流量，须本轮修 |
| **P1** | **9** | 版式错位、资源泄漏、竞态回退失效，建议本轮或下轮修 |
| **P2** | **5** | 技术债与生产开关，记录待排期 |

**总判断（一句话）**：7 个问题里 **6 个（①③④⑤⑥⑦）是实现缺陷**，不是"Linux 只能这样"；
只有 ② 属于"ffmpeg 子进程替代 MediaPlayer"的**有意平台偏离**（`docs/09-LINUX-DIVERGENCES.md:61` 有记录），
但这条偏离把上游"一次下载、本地循环播放"的缓存收益一并丢了，**偏离的必要性成立，偏离的实现不成立**。
⑦ 的版本字段与上游同口径，观感"过旧"来自失败兜底展示了自检用的假版本号。

**问题 ① 不是单一 bug，是三层叠加**：

1. 每次切换区服/档案，`GameChanged` 至少触发两次（`ShellViewModel.cs:242` + `:744`），
   `StarwardShell` 收到后清空并**整页重建** `GameLauncherPage`（`StarwardShell.axaml.cs:109-125`）；
2. 新页面构造即 `RefreshBackgroundImages()`（`GameLauncherPage.axaml.cs:40`）→ 重新拉官方背景目录
   （`BackgroundService.cs:175-204`，无缓存）→ `BackgroundImages.Clear()` + 逐条 `Add`；
3. 加载完成后只要列表非空就**强制回到第 0 张**（`GameLauncherPageViewModel.cs:1391-1394`，不恢复上次选择），
   且切换动作本身无取消/无去抖（`:1534-1548`、`:1558-1579`）。于是用户看到的是"闪一下、回到第一张、再闪"。

### 2.2 背景缓存与播放（②）

**我们的实现**

- 缓存目录：`src/LunarWard.Platform/XdgPaths.cs:103` `~/.cache/lunarward/background`，
  经 `BackgroundService.cs:134 CacheDirectory => _paths.BackgroundDirectory` 暴露；
  `Discover()` 只扫这个目录（**本地自定义图**）。官方**静态图**经 `StarwardAssets.CacheAsync` 落盘到
  `~/.cache/lunarward/starward/background-<hash>.<ext>`（`:58`、`:302`，有下载单飞），
  **官方视频从不落盘**，由 ffmpeg 直接读 `https` URL。
- `BackgroundService.cs:175-204` `LoadCatalogAsync`：每次页面构造都
  `new HoYoPlayClient(_http).GetGameBackgroundAsync(launcherId, "zh-cn", gameId)`，**无 TTL、无 ETag、无单飞**；
  失败只 `ProbeError ??= ex.Message`。
- 播放：`Services/VideoBackgroundPlayer.cs`，ffmpeg 子进程 → `WriteableBitmap`。
  `:43` `FrameBytes = 1280*720*4 = 3.69MB`；`:46` `MaxFrameRate = 24`；
  `:110` `-stream_loop -1`；`:115` `-vf scale=1280:720:...,crop=1280:720,fps=24`；
  `:116-118` `-pix_fmt bgra -f rawvideo pipe:1`。
  `:185-215` `PumpAsync` **每帧 `new byte[FrameBytes]`**（24fps × 3.69MB ≈ **88 MB/s 分配**），
  再 `Dispatcher.UIThread.InvokeAsync` 里 `Marshal.Copy` 整帧 3.69MB（**UI 线程每帧拷贝**）后 `InvalidateVisual`。
- 源可以是 `https://...mp4`（`BackgroundEntry.VideoSource` 直接是 URL）：`-stream_loop -1` 在 HTTP 源上是
  **每轮重连重下**，带宽按循环次数线性放大。
- 另外：`:180` `_firstFrame` 是 `readonly` 字段且只在首帧到达时 `TrySetResult()`（`:214-217`），
  `Stop()`（`:322-330`）不重置它 → 第二次 `StartAsync` 的"等首帧 3s"（`:165-174`）`Task.WhenAny`
  直接命中已完成的 TCS、立即通过，坏流不再回退；`:326` `Stop()` 里 `_pump.Wait(1s)` **同步阻塞 UI 线程**。

**上游实现**

- `src/Starward/Features/Background/BackgroundService.cs:41-48` 缓存路径固定
  `Path.Join(AppConfig.CacheFolder, "bg", name)`；`:167-215` `GetBackgroundFileAsync` 先 `File.Exists`，
  不存在才下载字节落盘（**一次下载，之后本地播放**）；`:82-86` `FileIsSupportedVideo` 支持 `.mp4/.mkv/.webm`；
  `:215-260` 有按尺寸/时间的清理策略。
- `AppBackground.xaml.cs:397` `MediaPlayer` + `IsVideoFrameServerEnabled = true`、`:492` `CopyFrameToVideoSurface`
  → 系统硬解、本地文件循环不重下；`:94-102` `PlacehoderImageSource` 防闪黑；
  `:153-165` 取消上一次；`:216-244` 同文件跳过重启。
- `docs/09-LINUX-DIVERGENCES.md:61` 已记录我们"ffmpeg 子进程、https 直读、1280×720/24fps"的偏离理由
  （LibVLC `VideoView` 在 Wayland 全黑、`vmem` 在 Arch 缺解码器），**这条偏离本身合理**。

**差异性质**：平台偏离（ffmpeg）+ 实现缺陷（缓存缺失、每帧分配、UI 线程拷贝）。

**修复建议**

1. **保留 ffmpeg，但学上游先落盘**：新增 `BackgroundVideoCache`，用
   `StarwardAssets.cs:255-310` 已经验证过的 `_downloadTasks.GetOrAdd` 单飞 + SHA256 落盘模式
   （`CacheAsync(url, "bgvideo")`），ffmpeg 改读本地文件。这一步同时解决带宽与 loop 重连。
2. `PumpAsync` 改**环形缓冲/复用缓冲**：预分配 3~4 个 `byte[FrameBytes]` 轮转，
   用 `ArrayPool<byte>.Rent` 更省；UI 侧改 `WriteableBitmap` 直接 `Lock()` 后 `Marshal.Copy` 到
   `locked.Address`（**去掉中间 `frame` 数组**），并考虑降到 30fps 以下的 960×540 在 1280 宽窗口下几乎无差。
3. `Stop()` 里 `_pump.Wait(1s)` 改为 `await _pump.WaitAsync(ct)`，Stop 走 async 路径，禁止阻塞 UI 线程。
4. `Stop()` 时重置 `_firstFrame`（改成 `TaskCompletionSource?` 字段，每次 `StartAsync` 新建）。
5. `LoadCatalogAsync` 加 30 分钟 TTL + `ConcurrentDictionary<string, (DateTimeOffset At, BackgroundCatalog Catalog)>`，
   并与上游一致按 `gameId` 分键；页面重建时不再打接口。
6. 可选：窗口不可见/最小化时 Pause（上游 `MainWindowStateChanged` 有 `Pause/Play`），我们已有
   `Pause/Resume`（SIGSTOP/SIGCONT）但没人调用 —— 见 P1-7。

### 2.7 包体版本（⑦）

**我们的实现**

- `src/LunarWard.App/Views/Starward/GameLauncherSettingDialog.axaml.cs:240-283` `LoadPackageVersionsAsync`：
  1. `GetGameBranchAsync` → `LatestPackagesTab.Header = branch?.Main?.Tag`（先展示分支标签）；
  2. `context.Services.Installer.GetGamePackageAsync(launcherId, language, gameId)` →
     `main.Major?.Version` 覆盖 Header（**与上游同口径**：`GamePackage.Main.Major.Version`）；
  3. **catch（`:278-283`）不记日志**，直接
     `LatestPackagesTab.Header = $"{Strings["LauncherSetting.LatestVersion"]} —";`
     `PreDownloadRunFallback(); SeedPackagesForCapture();`
- `:614-616` `SeedPackagesForCapture()` **硬编码** `正式版版本 6.2.0` / `预下载版本 6.3.0`，
  并塞入 `example.invalid` 假包体（`:620-640` 起）。这是自检截图用的函数，被 catch 兜底真实调用。
- 接口层正确：`src/LunarWard.Core/HoYoPlay/HoYoPlayClient.cs:213-219`
  `url += $"&game_ids[]={gameId.Id}"`，`return list.FirstOrDefault(x => x.GameId == gameId)`；
  `CommonGetAsync`（`:43-62`）无缓存、无 ETag；`src/LunarWard.Installer/GameInstallController.cs:82-90` 只是透传，无缓存。

**上游实现**

- `Features/GameLauncher/GameLauncherSettingDialog.xaml.cs:973` `LatestVersion` 属性；
  `:996-1000` `var gamePackage = await _hoyoPlayService.GetGamePackageAsync(CurrentGameId); LatestVersion = gamePackage.Main.Major!.Version;`
  catch 里只 `_logger.LogError(...)`，**不写任何假数据**（UI 留空/保持 `—`）。
- `Features/HoYoPlay/HoYoPlayService.cs:176-189` `GetGamePackageAsync(GameId gameId)`：
  MemoryCache 键 `$"{nameof(GamePackage)}_{gameId.Id}"`、TTL 1 分钟、`list.FirstOrDefault(x => x.GameId == gameId)`。

**差异性质**：**不是有意偏离**，是自检代码进了生产兜底路径；版本字段口径与上游完全一致。

**判定（明确回答 Lead 的问题）**："用户觉得版本过旧"**不是我们取错字段**，也不是缓存旧值
（`GetGamePackageAsync` 链路零缓存）；是**请求失败时展示了硬编码的 6.2.0/6.3.0**，
而这两个数字停留在自检快照的时点。任何让 `game_ids[]` 请求失败的原因（区域网络、launcherId 与 gameId 不匹配、
`main.Major` 为 null 的预下载包）都会触发它。

**修复建议**：

1. catch 里**删掉** `SeedPackagesForCapture()`，改为 `Header = "—"` + 记 `_logger.LogWarning(ex, ...)`；
   `SeedPackagesForCapture()` 仅在 `CaptureMode` 为自检时调用。
2. 增加"失败可见"：失败时在版本行旁显示 `不可用（重试）` 按钮，而不是静默显示假版本。
3. 对齐上游 1 分钟 MemoryCache（按 `gameId.Id`），避免同一个对话框反复请求。
4. 断网/`example.invalid` 场景加一条单测：断言失败路径不产生 `6.2.0`。
